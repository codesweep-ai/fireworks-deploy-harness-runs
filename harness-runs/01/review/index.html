Approval-slice rules — task-tracker-demo @ eee783057ec28d28fb36ec05484de9b4b40ceb9c (frozen ~/app)

Slice: approve/reject on POST /tasks/action. All paths relative to src/main/java/com/acme/tracker/ unless noted. Current behavior only; no intended-policy claims.

R-APR-001 — Filter-level approver gate on /tasks/action

- Source: web/AuthFilter.java:40-47 (mapped to /* by src/main/webapp/WEB-INF/web.xml:20-23)

- Actors: any authenticated user (session attribute user non-null; unauthenticated is handled earlier at AuthFilter.java:33-38 by 302 redirect to /login).

- Preconditions: request reached the filter; path is /tasks/action (not one of the /login, /api/*, *.css exemptions at AuthFilter.java:28-31); user authenticated.

- Trigger: POST /tasks/action with action = approve or reject.

- Effects: if user.getRole().canApprove() is false → 403 Forbidden, body message "Only managers or admins may approve or reject tasks"; request never reaches the servlet. Otherwise chain continues.

- Refusal behavior: 403, no DB write (filter runs before any DAO call).

- Confidence: high (direct code). Ambiguity: none.

R-APR-002 — Servlet-level approver re-check (defense-in-depth duplicate)

- Source: web/TaskActionServlet.java:91-98 (requireApprover), invoked at :49 (approve) and :54 (reject).

- Actors/preconditions: user already passed the filter (authenticated) AND task id parsed and found (404 at :31-36 happens first).

- Trigger: approve/reject switch cases.

- Effects: if user == null || !user.getRole().canApprove() → 403, message "Approval requires a manager or admin".

- Refusal behavior: 403, no DB write (checked before guard and updateStatus).

- Confidence: high. Disagreement record (filter vs servlet): the two layers use the *same predicate* (Role.canApprove()) but different messages, and the filter fires first on every normal route to /tasks/action (no exemption covers it), so the servlet's 403 message is unreachable through the standard route. No outcome-level disagreement — only duplicated enforcement and divergent refusal text. Also note check ordering: existence (404) precedes the servlet role check, but the filter role check precedes existence — so a non-approver probing a nonexistent id sees 403 (filter), not 404; an approver sees 404.

R-APR-003 — Definition of "may approve" (the deciding code path)

- Source: model/Role.java:13-16 — canApprove() returns this == ADMIN || this == MANAGER.

- Actors: roles ADMIN, MANAGER pass; MEMBER, VIEWER refuse. This is decided by this method (called from AuthFilter.java:42 and TaskActionServlet.java:93), not inferred from role names.

- Preconditions/trigger: n/a (pure predicate).

- Effects: defines the approver set for R-APR-001/002.

- Refusal behavior: n/a.

- Confidence: high. Related but non-deciding: db/schema.sql:14-15 CHECK only constrains person.role to the four legal values — it grants no approval rights and does not mirror canApprove.

R-APR-004 — Starting-state guard: approve/reject require PENDING_APPROVAL

- Source: web/TaskActionServlet.java:48-57 (approve :48-52, reject :53-57) + guard() at :100-109; invoked at :50 and :55 with expected = TaskStatus.PENDING_APPROVAL.

- Actors: any user who passed the approver checks (R-APR-001/002).

- Preconditions: task exists; user is an approver.

- Trigger: approve or reject on a task whose status != 'PENDING_APPROVAL'.

- Effects: 409 Conflict, message "Cannot <action> a task in status <current> (expected PENDING_APPROVAL)"; no DB write.

- Refusal behavior: 409; task row untouched (observable via oracle SELECT id,status FROM task ORDER BY id).

- Confidence: high. Ambiguity: none.

R-APR-005 — Transitions and persistence for successful approve/reject

- Source: web/TaskActionServlet.java:51 (approve → TaskStatus.DONE), :56 (reject → TaskStatus.IN_PROGRESS); write via dao/TaskDao.java:115-125 updateStatus — unconditional UPDATE task SET status=?, updated_at=CURRENT_TIMESTAMP WHERE id=?.

- Preconditions: R-APR-001..004 all passed.

- Effects: new status persisted; updated_at bumped; response 302 redirect to /tasks (or /tasks/form?id=<id> when return=detail, :66-73).

- Refusal behavior: n/a (success rule).

- Confidence: high. Note: the status precondition lives *only* in the servlet; neither updateStatus SQL nor db/schema.sql:33 (CHECK enumerates the four statuses, not transitions) enforces it. DAO/DB would accept any legal status from any current status — the guard is single-point in TaskActionServlet.

Gaps (discovered, deliberately not expanded into this pilot)

- G-APR-001: bulkClose (web/TaskActionServlet.java:26-29, 76-88; dao/TaskDao.java:128-147) sets any non-DONE task to DONE in one UPDATE with no canApprove check and no PENDING_APPROVAL guard — a MEMBER/VIEWER can reach DONE (approve-equivalent) via POST /tasks/action?action=bulkClose&ids=…. Out of slice; flagged for orchestrator.

- G-APR-002: Long.parseLong(req.getParameter("id")) at TaskActionServlet.java:31 throws NumberFormatException (unhandled → 500) on missing/malformed id. Out of slice.

- G-APR-003: /api/* is exempt from AuthFilter (AuthFilter.java:28) but web/ApiTaskServlet.java is GET-only read-back — no approval bypass there (verified).

EARS specs — approval slice — task-tracker-demo @ eee783057ec28d28fb36ec05484de9b4b40ceb9c

System under specification: the task-tracker web app (frozen ~/app). All specs are current behavior, derived from the sources cited in rules/R-APR.md.

S-APR-001 — approve success (state + event driven)

While the authenticated user's role satisfies canApprove() (ADMIN or MANAGER, per model/Role.java:14-16) and the target task's status is PENDING_APPROVAL, when the system receives POST /tasks/action with action=approve and id of that task, the system shall set that task's status to DONE, refresh its updated_at, and respond 302 redirecting to /tasks.

- Observable: HTTP 302 with Location: /tasks; oracle SELECT id,status FROM task ORDER BY id shows the task DONE.

S-APR-002 — reject success (state + event driven)

While the authenticated user's role satisfies canApprove() and the target task's status is PENDING_APPROVAL, when the system receives POST /tasks/action with action=reject and id of that task, the system shall set that task's status to IN_PROGRESS, refresh its updated_at, and respond 302 redirecting to /tasks.

- Observable: HTTP 302; oracle shows the task IN_PROGRESS.

S-APR-003 — role refusal (unwanted behavior)

When the system receives POST /tasks/action with action=approve or action=reject, if the authenticated user's role does not satisfy canApprove() (MEMBER or VIEWER), then the system shall respond 403 Forbidden and leave the task's status unchanged.

- Observable: HTTP 403; body contains "Only managers or admins may approve or reject tasks" (filter message, web/AuthFilter.java:42-45 — fires before the servlet's own check); oracle shows task status unchanged. (If the filter were bypassed, the servlet's requireApprover, web/TaskActionServlet.java:93-95, yields 403 with "Approval requires a manager or admin" — same outcome, different text; see rules/R-APR.md disagreement record.)

S-APR-004 — wrong-starting-state refusal (unwanted behavior)

When an authenticated user whose role satisfies canApprove() sends POST /tasks/action with action=approve or action=reject, if the target task's status is not PENDING_APPROVAL, then the system shall respond 409 Conflict and leave the task's status unchanged.

- Observable: HTTP 409; body matches Cannot <action> a task in status <current> (expected PENDING_APPROVAL) (web/TaskActionServlet.java:101-108); oracle shows task status unchanged.

S-APR-005 — unauthenticated request (supporting precondition)

When the system receives POST /tasks/action with action=approve or action=reject, if no authenticated user is bound to the session, then the system shall respond 302 redirecting to /login and leave the task's status unchanged.

- Observable: HTTP 302 Location: /login (web/AuthFilter.java:33-38); oracle unchanged.

All five cases are source-supported; none was unsupported. Coverage note: (a)=S-APR-001/002, (b)=S-APR-003, (c)=S-APR-004 per dispatch item 2.

"""Reusable real-HTTP plumbing for task-tracker tests (Python stdlib only).

Base URL is http://127.0.0.1:8080 (override with TT_BASE_URL). Each test case
gets its own cookie jar, i.e. its own session. Redirects are NOT followed, so
tests can assert on 302/Location themselves. 4xx/5xx responses are returned as
response objects instead of raising.
"""
import http.cookiejar
import os
import unittest
import urllib.error
import urllib.parse
import urllib.request

BASE_URL = os.environ.get("TT_BASE_URL", "http://127.0.0.1:8080").rstrip("/")


class _NoRedirect(urllib.request.HTTPRedirectHandler):
    def redirect_request(self, req, fp, code, msg, headers, newurl):
        return None


class HttpCase(unittest.TestCase):
    """Base class: session-cookie HTTP client plus login/action helpers."""

    def setUp(self):
        self.jar = http.cookiejar.CookieJar()
        self.opener = urllib.request.build_opener(
            urllib.request.ProxyHandler({}),
            urllib.request.HTTPCookieProcessor(self.jar),
            _NoRedirect(),
        )

    def request(self, method, path, params=None):
        data = None if params is None else urllib.parse.urlencode(params).encode()
        req = urllib.request.Request(BASE_URL + path, data=data, method=method)
        try:
            return self.opener.open(req, timeout=10)
        except urllib.error.HTTPError as exc:  # 4xx/5xx are answers, not crashes
            return exc

    def login(self, username, password):
        """POST /login. Success: 302 to /tasks + JSESSIONID cookie.
        Failure: 200, login page with 'Invalid credentials'."""
        return self.request("POST", "/login", {"username": username, "password": password})

    def task_action(self, task_id, action, **extra):
        """POST /tasks/action as the currently logged-in user."""
        params = {"id": str(task_id), "action": action}
        params.update(extra)
        return self.request("POST", "/tasks/action", params)

    def session_cookie(self):
        return next((c for c in self.jar if c.name == "JSESSIONID"), None)

"""Approval-slice tests: one per accepted EARS spec (S-APR-001..005).

Specs: specs/S-APR.md; rules: rules/R-APR.md; fixtures/oracle expectations:
evidence/analyst/fixtures.md (commit d7e6bdf). Persisted-state assertions go
through the read-only oracle (`harness/runtime.py sql`), not HTML scraping.
Mutating cases reset the seat's isolated database first so task 3 is
PENDING_APPROVAL again; no reliance on test order or generated ids.
"""
import subprocess
import unittest
from pathlib import Path

from httpcase import HttpCase

OUTPUTS = Path(__file__).resolve().parent.parent


def reset_db():
    subprocess.run(
        ["python3", "harness/runtime.py", "reset"],
        cwd=OUTPUTS, check=True, capture_output=True, text=True,
    )


def oracle_statuses():
    """Read-only oracle: {id: status} from `SELECT id,status FROM task`."""
    out = subprocess.run(
        ["python3", "harness/runtime.py", "sql",
         "SELECT id,status FROM task ORDER BY id"],
        cwd=OUTPUTS, check=True, capture_output=True, text=True,
    ).stdout
    return {int(line.split("|")[0]): line.split("|")[1].strip()
            for line in out.strip().splitlines()}


class TestApproveSuccess(HttpCase):
    """S-APR-001 (rules R-APR-001, R-APR-003, R-APR-004, R-APR-005):
    mgr approves task 3 (PENDING_APPROVAL) -> 302 to /tasks; task 3 DONE,
    all other tasks unchanged."""

    def setUp(self):
        super().setUp()
        reset_db()

    def test_s_apr_001_mgr_approve_task3(self):
        r = self.login("mgr", "mgr")
        self.assertEqual(302, r.status)
        self.assertIsNotNone(self.session_cookie())
        r = self.task_action(3, "approve")
        self.assertEqual(302, r.status)
        self.assertEqual("/tasks", r.headers.get("Location"))
        self.assertEqual(
            {1: "OPEN", 2: "IN_PROGRESS", 3: "DONE", 4: "DONE"},
            oracle_statuses(),
        )


class TestRejectSuccess(HttpCase):
    """S-APR-002 (rules R-APR-001, R-APR-003, R-APR-004, R-APR-005):
    admin rejects task 3 (PENDING_APPROVAL) -> 302 to /tasks; task 3
    IN_PROGRESS, all other tasks unchanged."""

    def setUp(self):
        super().setUp()
        reset_db()

    def test_s_apr_002_admin_reject_task3(self):
        r = self.login("admin", "admin")
        self.assertEqual(302, r.status)
        r = self.task_action(3, "reject")
        self.assertEqual(302, r.status)
        self.assertEqual("/tasks", r.headers.get("Location"))
        self.assertEqual(
            {1: "OPEN", 2: "IN_PROGRESS", 3: "IN_PROGRESS", 4: "DONE"},
            oracle_statuses(),
        )


class TestRoleRefusal(HttpCase):
    """S-APR-003 (rule R-APR-001): dev (MEMBER, canApprove=false) attempts
    approve on task 3 -> 403 'Only managers or admins may approve or reject
    tasks'; no mutation, task 3 stays PENDING_APPROVAL."""

        )


class TestWrongStateRefusal(HttpCase):
    """S-APR-004 (rule R-APR-004): mgr approves task 1 (OPEN, not

    """S-APR-005 (rule R-APR-001): no login; POST approve id=3 -> 302 to

"""Harness smoke tests: prove real-HTTP + session-cookie plumbing works.

EARS-tagged rule tests land in a follow-up dispatch; this module keeps
`python3 harness/runtime.py test` non-empty and validates the login helper.
"""
import unittest

try:  # imported as top-level module by unittest discovery (start dir = tests/)
    from httpcase import HttpCase
except ImportError:  # imported as part of the tests package
    from tests.httpcase import HttpCase


class TestSkeleton(HttpCase):
    def test_login_page_served(self):
        resp = self.request("GET", "/login")
        self.assertEqual(resp.status, 200)
        self.assertIn(b"Sign in", resp.read())

    def test_anonymous_is_redirected_to_login(self):
        resp = self.request("GET", "/tasks")
        self.assertEqual(resp.status, 302)
        self.assertTrue(resp.headers["Location"].endswith("/login"))

    def test_login_success_redirects_and_sets_session_cookie(self):
        resp = self.login("mgr", "mgr")
        self.assertEqual(resp.status, 302)
        self.assertTrue(resp.headers["Location"].endswith("/tasks"))
        self.assertIsNotNone(self.session_cookie())
        self.assertEqual(self.request("GET", "/tasks").status, 200)

    def test_login_failure_returns_login_page_with_error(self):
        resp = self.login("mgr", "wrong-password")
        self.assertEqual(resp.status, 200)
        self.assertIn(b"Invalid credentials", resp.read())
        # NB: JSP rendering sets JSESSIONID even on failure; the cookie alone
        # is not proof of auth — the session must also reach /tasks.
        self.assertEqual(self.request("GET", "/tasks").status, 302)


if __name__ == "__main__":
    unittest.main()
