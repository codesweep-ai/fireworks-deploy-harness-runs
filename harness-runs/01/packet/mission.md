# Run 01: a 15-minute business-rule testing pilot

Extract and test one coherent approval/permission slice of the frozen task-tracker-demo
application. Prove this team's discovery → EARS specification → executable test → independent
verification loop works, and leave concrete evidence of any obstacle for the next numbered run.

The application snapshot is `~/app`; your writable output repository is `~/outputs`.
Its `_campaign/` directory records the exact application commit, expected source hashes, and policy.
Run `python3 harness/check-frozen-app.py ~/app` before and after testing.
All authored work belongs in the output repository, never the application snapshot.

## Prepared runtime and operator launch gates

The pinned app/database images are prewarmed in the shared image store. Runtime smoke verified
startup, database reset, coverage collection, and unchanged application sources inside a real
Firecracker sandbox. Runtime jars arrive at `~/runtime`. From `~/outputs`, use:

```
python3 harness/runtime.py start
python3 harness/runtime.py reset
python3 harness/runtime.py sql 'SELECT id,status FROM task ORDER BY id'
python3 harness/runtime.py fixture 'UPDATE task SET status=... WHERE id=...'
python3 harness/runtime.py test
python3 harness/runtime.py coverage
```

HTTP is local to each member at `http://127.0.0.1:8080`. `sql` uses the read-only database oracle;
`fixture` explicitly writes test data. `test` runs Python unittest discovery and rejects an empty
suite. No tests have been generated by the host. The seeded users and data are in the snapshot.
Each member starts its own app/database; the shared store contains images, never live test state.

The host-side launcher supervises creation and observation independently, starts collection with
three minutes left, and initiates stopping every member at the 15-minute cutoff. Slow observation
and collection were tested not to delay the stop timer. Disks are retained. Live model/credential
readback is checked by `create`; a failure is a measured pilot finding, not permission to retry
beyond the run budget. Any preparatory commit requires regenerating this packet.

## Acceptance

1. `rules/` and `specs/` describe the selected approval permission and status conditions with
   stable IDs and source-file/line citations to this snapshot. Test specifications use EARS.
   Include an allowed action, a role refusal, and a wrong-starting-state refusal, or explicitly
   explain a source-supported reason one does not apply.
2. Executable tests drive real HTTP requests through the app's authentication filter and servlet.
   They assert responses and persisted effects, including unchanged task state after refusals.
   Each test names its EARS/rule IDs. Tests and tooling live outside the frozen app.
3. The verifier runs the integrated tests independently against its own app/database, at a named
   commit, and saves commands, exit codes, results, and application-integrity checks.
   A suspected failure is reproduced and tracked rather than silently removed or redefined.
4. Record line/branch coverage of the frozen Java application if the prepared collector works.
   State the measured source scope and commands. If collection fails, retain the failure as an
   unmet goal; never fabricate a percentage, narrow the denominator, or delay closeout to chase it.
5. The orchestrator leaves `reports/run-summary.json`, `reports/attempts.json`, and
   `findings/ledger.json` with integrated output commit(s), achieved and unmet goals, measurements,
   adjudications, and next-run recommendations. An empty findings ledger is an explicit empty list.
6. Application source hashes match before and after execution. Any mismatch is a campaign failure,
   regardless of test results. No edits to Java, JSP, SQL, build files, dependencies, or app scripts.

## Time and attempt policy

- The 15-minute wall clock begins at campaign creation, including provisioning and readback.
  Use the exact deadline supplied by the campaign; do not restart a fresh 15-minute clock.
- Each stable work item gets at most two attempts: initial submission and one correction after
  verification. Each attempt has a three-minute budget, further bounded by time left before
  closeout. Tool/model calls within an attempt are not restricted to two.
- Record item ID, owner, attempt number, dispatch ID, timestamps, result, and verification evidence.
  Relabelling the same unresolved issue does not reset its allowance. Briefing readbacks are not
  work attempts. On exhaustion, retain the evidence and move on to another feasible item.
- Stop opening new work no later than three minutes before the deadline. Commit available work,
  record gaps, integrate what is verifiable, and reply before cutoff. Do not spend the reserve on
  further implementation. The host collects evidence and stops nodes at cutoff, retaining disks
  if collection is incomplete. The native deadline alone does not enforce a hard stop.

## Frozen app and findings

The orchestrator adjudicates findings as suspected defect, confirmed defect, not a defect, or
unresolved. Record expected versus observed behavior, rule/test IDs, reproduction evidence,
source commit, and rationale. Source behavior does not by itself establish intended policy.
Keep tests characterizing observed behavior distinguishable from intended-requirement checks.
Confirmed defects retain reproducers and unmet requirements; they never authorize an app fix.

## Boundaries and closeout

No app changes, broad refactoring, whole-app modelling, full role/state cartesian product, or
coverage target for this pilot. No new provider/model choice or extra seat. A missing runtime,
provider, or prepared harness is an infrastructure finding, not a request to spend the run building
a platform. Return partial work promptly. Report `campaign-met` only if every acceptance condition
holds; otherwise name unmet goals and choose the outcome that explains why work stopped.
